## Parsing: How Atf Text Becomes   `atf_tokens.csv`,  `grapheme.csv` and  `warnings.csv`

This step takes real ATF transliteration text, together with the sign catalogue built in the Dataset stage (`allograph_all_v11.csv`, `compound_form_reading_table.csv`), and produces a token-by-token record of a corpus.    
Two scripts carry this out in sequence: `1_transferTrLit_Sign.py` reads raw ATF and produces `atf_tokens.csv` (one row per word-token) plus one `{P-number}.txt` per tablet; `2_txt_to_grapheme.py` reads `atf_tokens.csv` together with CDLI's own artifact metadata and expands every token into `grapheme.csv` (one row per actual sign occurrence, compounds exploded into their verified components).

```
ATF file, CDLI metadata (artifacts_*.csv) pass through  1_transferTrLit_Sign.py  produce  atf_tokens.csv  +  {P-number}.txt

2_txt_to_grapheme.py produces  grapheme.csv  +  warnings_grapheme.csv
```
## Data Sources

| Source | Description |
|---|---|
| **allograph_all_v11.csv** (Dataset Step 4 output) | Sign catalogue: every atomic sign's own reading, and every compound's verified component list. |
| **compound_form_reading_table.csv** (Dataset Step 3 output) | Compound whole-word reading, split into `attested_compound_dict` (real) and `inferred_compound_dict` (joined guess, never treated as fact). |
| **CDLI `artifacts_{artifact_id}.csv`** | One file per tablet, CDLI's own structured files: `provenience`, `period`, `genres`, `languages`, plus CDLI's own uncertainty flags and `is_school_text`. Primary metadata source. |
| **ATF files** | One file per tablet, the transliteration itself. |

## Pipeline Overview

| Stage | Task | Note |
|---|---|---|
| **Stage 1** | Load `simple_dict`, `attested_compound_dict`, `inferred_compound_dict` from the Dataset catalogue | three normalised tables |
| **Stage 2** | Preprocess each line: ASCII-to-Unicode diacritics, `@`-modifier codes, damage/editorial flags, inline `($ ... $)` and `\|\|`-apparatus comments, determinative extraction | one cleaned line, written to both `{P-number}.txt` and used as the tokenizer's input |
| **Stage 3** | Tokenize each word| `atf_tokens.csv` |
| **Stage 4** | Verify `compound sign` token, skip `numeral`/`broken`/`unresolved` tokens entirely, attach CDLI metadata | `grapheme.csv` |
| **Stage 5** | Collect every unresolved name, grouped by (name, provenance, period) | `warnings_grapheme.csv` |

## Step-By-Step Description

**1. Line Preprocessing.**      
ASCII diacritic conversion (`sz`→š, `s,`/`s'`→ṣ, `t,`/`t'`→ṭ), `@`-modifier table (`@x`→×, `@\`→`@t`, etc.), combining-diacritic folding (`g̃`→g, `ḫ`→h), damage/editorial glyph strip (`#`, `<...>`, `<<...>>`), and inline `($ ... $)` structural-comment removal. `||`-Apparatus Lines, literary/composite editions cite parallel manuscript witnesses using lines like `>>A 122`,`||B 238` (was **not** filtered — `|` was missing from the line-skip character class). The line number from the OTHER manuscript (`238`) was leaking through as if it were real sign content. Fixed by adding `|` to the skipped-line prefix set

**3. Determinatives.**   
`{d}`, `{ki}`, `{giš}`... stripped before tokenisation, recorded in their own `determinative` column. A determinative with no separator on either side is replaced with a hyphen, not deleted outright, to avoid fusing neighbouring signs into a phantom sequence. **Found in testing:** two determinatives sitting directly adjacent with nothing between them (`{disz}{d}suen-...`) produced a **leading hyphen** at the very start of the word, which then created an empty split-piece downstream.

**4. Numerals And Broken**     
 ATF numerals (`1(diš)`, `n(iku)`) and the collapsed ellipsis `…` (from `[...]`, meaning damaged/missing text) are not real signs, so they are recognised before any dictionary lookup happens, and are never searched for in the sign dictionaries at all.    
This check happens at two levels: on the whole word by itself, and separately on each piece inside a longer hyphenated word. The second level was needed because a numeral or the ellipsis sometimes gets fused to real content by a hyphen, for example `2(disz)-kam` or `…-ka-du`. Checking only the whole word misses these cases completely, since the whole word here is not a pure numeral or a pure ellipsis — it is a numeral plus something else attached.    
The ellipsis check needed this fix for one more reason: `allograph_all_v11.csv` happens to contain a real, unrelated sign named `xxx`, whose own attested reading is literally the text `…`. Without the fix, every damaged-text marker in the corpus was being silently matched to this one placeholder sign, instead of being recognised as damaged text.

**5. Tokenisation.**  
Space is always the outer boundary. A compound reading is never allowed to cross from one word into the next. Inside one word, hyphen and dot together mark the inner boundaries, between individual signs.   
When looking for a compound inside a word, the search always tries the longest possible span first, only falling back to shorter spans if nothing longer matches.          
The first pass checks only real, attested readings (`attested_compound_dict`), across the entire word. Only after this first pass is completely finished does the second pass begin, checking the remaining, still-unmatched pieces against the weaker, guessed readings (`inferred_compound_dict`).     
Sometimes a whole word has no hyphen or dot at all, and yet it is still a complete, real compound reading by itself.

**6. Token Priority Correction** 
`simple_dict` is checked **before** `attested_dict` for any single piece. 
The `source` field for a single-piece compound match is filled in the exact same way as for any other compound match, always one of `OSL`, `DIRI`, `OGSL`, `SYLLABARY_CM`, or left empty. 

**7. The `r.`/`v.` prefixes**     
ATF sometimes uses short prefixes like `r.` or `v.` to reference another line (for example "see the reverse side"). These prefixes are not signs, so they must never be split as if the dot inside them marked a compound. Only the short prefix itself (`r.`) is cut off and kept as its own separate token. Whatever comes after it is tokenised normally

**8. Compound Expansion.** 
Every token marked as a `compound` gets turned into several rows in the output, one row for each sign that makes up that compound. If a compound has three components, it becomes three rows, each with its own `component_position` showing where it sits in the sequence.
These components are not worked out again from scratch here. They are taken directly from `allograph_all_v11.csv`, where this exact breakdown was already established and checked in an earlier step. The script does not re-read or re-analyse the compound's name to guess its parts a second time, it simply looks up the already-verified list.

**9. `sign_type` assignig of `LOGO`, `SYLL`, `NUMERAL`,`UNKNOWN`**   
Whether a sign is marked `LOGO` (used for its meaning) or `SYLL` (used for its sound) is decided by looking at the exact letters as they appear in the original ATF text( capital or lowercase) never by looking at the dictionary's own version of the sign's name. This was checked directly: a sample written entirely in lowercase produced only `SYLL` results, and after one line was changed to capital letters, it correctly produced `LOGO`.  
Compounds are never labelled `LOGO` or `SYLL` at all. A compound is  a whole word that was memorised as one unit, so this distinction simply does not apply to it.  
Rows marked `NUMERAL`, and rows that could not be resolved at all (`UNKNOWN`), are left out of `grapheme.csv` completely.    
`NUMERAL` are kept `atf_tokens.csv`   
`UNKNOWN` are kept  in `warnings_grapheme.csv`

**10. Metadata From CDLI's Own Export.**    
Metadata for each tablet is read directly from CDLI's own file (`artifacts_{artifact_id}.csv`).   
CDLI sometimes marks its own data as uncertain, for example, when it is not fully sure about a tablet's genre, period, or findspot. These uncertainty markers (`genre_uncertain`, `period_uncertain`, `provenience_uncertain`) are copied through exactly as CDLI recorded them, never decided or calculated here. The same applies to `is_school_text`, a flag CDLI uses to mark a tablet as a school exercise.    
Two fields from CDLI actually contain two pieces of information joined together, so each one is split into two separate columns.
The `period` field, for example `"ED IIIa (ca. 2600-2500 BC)"`, is split into `period_index` (`"ED IIIa"`) and `period_dates` (`"ca. 2600-2500 BC"`).
The `provenience` field, for example `"Shuruppak (mod. Fara)"`, is split into `provenance` (`"Shuruppak"`, the ancient name) and `modern` (`"Fara"`, the modern name for the same place today).

**11. Warnings File**
Unresolved names are  grouped together in `warnings_grapheme.csv` with the place and period it came from, so the same word failing in two different periods produces two separate rows.
Each row shows: the unresolved name itself, where it comes from (provenance and period), how many times exactly this combination occurred, and one real example `word_id`( a way to trace the row back to one specific occurrence in the source text.)


## Output: atf_tokens.csv

One row per word-token occurrence in the corpus, before compound expansion. One file for the whole corpus (not one per tablet).    
**How It Is Built**
Each line is cleaned once (diacritics, ATF markers, damage flags) and that same cleaned line is used both for the `.txt` file and for splitting into tokens.Tokens tokenised by space first, then by hyphen or dot together within each word, always trying the longest match first and falling back to shorter spans only when nothing longer is found. Real attested compound readings are always checked before  guesses compounds.

### Columns

●	**`p_number`** tablet identifier, from the ATF `&`-line.   
●	**`line_num`** transliteration line label, as given in the ATF.   
●	**`word_id`** `{p_number}_{sequential number}`.  
●	**`raw_atf_token`** the exact source text for this token (single sign or whole compound span), case untouched.   
●	**`resolved_name`** canonical `sign_name` (atomic) or `compound_form` (compound).  
●	**`token_kind`**  `atomic` / `compound` / `unresolved`.      
●	**`confidence`** `attested` / `inferred`, empty for atomic or unresolved.    
●	**`source`** `OSL` / `DIRI` / `OGSL` / `SYLLABARY_CM` for attested compounds, empty otherwise.    
●	**`determinative`**  semicolon-separated classifies stripped from this word, empty if none.

## 2. grapheme.csv

One row per **actual sign occurrence** a compound token becomes N rows, one per verified component, not one opaque row.

### How It Is Built

●	**Sign lookup is against `allograph_all_v11.csv`**, not a stale, disconnected catalogue. Compound components are the already-verified `component_position` / `unicode_id` / `sign_grapheme` triples already established in Steps 1–4 of the dataset pipeline — **not** re-derived by parsing `resolved_name` a second time here.
●	**`sign_type` is read from `raw_atf_token`, never from `resolved_name`.** A token that resolves to the canonical name `A` but was written lowercase `a` in the source is `SYLL`, regardless of how the dictionary happens to capitalise its own entries — confirmed by test: an all-lowercase sample produced only `SYLL`, and adding one uppercase line (`LUGAL AN`) correctly produced `LOGO` for exactly those two tokens.
●	**Compounds are never assigned LOGO or SYLL, at the word level or the expanded-component level.** A compound is a distinct third category of use — a memorised whole-word reading — not a point on the LOGO–SYLL spectrum, and its individual graphic components are not independently read at all; asking whether one piece of a diri-writing is "logographic" is a category error, not an open question. `sign_type = COMPOUND` is a complete, self-sufficient label for every row belonging to a compound token.
●	Every expanded component row of one compound token shares the same `sign_trlitScien` (the whole compound's name), the same `sign_phonetic` (the whole attested reading, e.g. `a-rin4-na`), and the same `word_id` — only `unicode_id` / `sign_grapheme` / `component_position` differ row to row, matching the convention already established for `compound_form` / `compound_grapheme` in the dataset pipeline.

### Columns

●	**`unicode_id`** for a compound row, these belong to this specific component, not the compound as a whole.
● **`sign_grapheme`** 
●	**`sign_trlitScien`**  canonical sign name, or the whole compound's name repeated across all its component rows.
●	**`sign_phonetic`** the original ATF reading (`raw_atf_token`, passed through unchanged).
●	**`sign_translation`**  reserved, not populated automatically.
●	**`sign_type`**  `LOGO` / `SYLL` / `NUMERAL` / `COMPOUND` / `UNKNOWN`.
●	**`is_compound`** `SIMPLE` / `COMPOUND`.
●	**`component_position`** 1-based position within the compound; empty for simple signs.
●	**`word_id`** — traces back to `atf_tokens.csv`.
●	**`confidence`** / **`source`** carried through from `atf_tokens.csv` unchanged.
●	**`artifact_id`, `corpus_id`, `genre_name`, `provenance`, `archaeological_context`, `period_index`, `period_dates`, `languages`** — from the ATF `&`/`#`/`@` header lines, unchanged in method from the original script.

## 3. warnings.csv / warnings_grapheme.csv

Two separate warnings files, one per script, deliberately not merged:

●	**`warnings.csv`** (Script: 1_transferTrLit_Sign_v12.py)  normalised tokens that matched nothing in any of the three dictionaries at the tokenisation stage. Columns: `normalized_token`, `count`.
●	**`warnings_grapheme.csv`** (Script:2_txt_to_grapheme_v12.py) names that came through as `resolved_name` from Script 1 but could not be found in `allograph_all_v11.csv` at expansion time (should be rare in practice, since Script 1 draws from the same catalogue; mainly a safety net for pipeline desyncs). Columns:  word_id,`unresolved_name`, `count`, sign_type, provenance, period_index.

Kept separate rather than combined because they diagnose two different failure points: a gap in the phonetic dictionaries (Script 1) and a gap or mismatch in the sign catalogue itself relative to what Script 1 already resolved (Script 2).
