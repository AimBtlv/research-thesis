## 4. How Was sign_catalogue_v13.csv Built?

**Note on the name:** this file was called `allograph_all_v11.csv` (`allograph_all_v12/v13.csv`) until 12 November 2026. The old name had nothing to do with the analysis of allographs (graphic forms of signs written by the scribes), which is Stage 3 of the thesis, so the file and two of its columns were renamed: `allograph_all` → **`sign_catalogue`**, `allograph_form` → **`osl_form`**, `graphic_variant_id` → **`osl_form_id`**. The data did not change (all 10,573 rows are identical). `osl_form` and `osl_form_id` describe *catalogue* forms recorded in OSL; the real form of a sign on a tablet will be the column `sign_variant_id` of grapheme.csv (Stage 3).

This step produces the complete sign dataset for every sign documented in the available sources:
- its Unicode identity;
- its structural composition (simple sign or compound, and if compound, exactly which components it decomposes into);
- its phonetic reading, drawing on Step 3's compound reading table wherever a sign is a compound.

This step takes the Unicode + Phonetic Version catalogue produced in Step 1 and the compound reading table produced in Step 3 and combines them with the ORACC Sign List (osl.asl) and the merged historical syllabary (CM + URUK2 + ADDITIONAL) to build a single table that answers, for every attested cuneiform sign, three questions:
1. What Unicode identity does it carry?
2. What is it built from, if it is a compound?
3. What phonetic readings does it have, as a sign of its own or as a compound?

osl.asl alone does not cover every sign a real text might contain, so a second goal of this step is to clarify which signs carry full Unicode-level verification and which do not.

## Pipeline Overview

The pipeline is built in seven stages over the full sign list:

| Stage | Task | Note |
|---|---|---|
| **Stage 1** | Parse every `@sign` and `@form` in `osl.asl`, skipping any block flagged `@sign-` / `@form-` / `@fake`. Classify each entity into `sign_type` and `sign_structure`. Decompose compounds into ordered components | One row per component position, covering all signs of `osl.asl` (8,172 rows) |
| **Stage 2** | Assign `osl_form_id` to every row, numbering each sign's distinct documented `@form`s (catalogue variants) in the order they appear in `osl.asl` | 6,109 distinct ids |
| **Stage 3** | Join phonetic data: atomic signs from the Step 1 catalogue by `unicode_id`; compounds from Step 3's reading table by `compound_form` | Columns `typePhonetic_Version` and `phonetic_version` filled on every row |
| **Stage 4** | Where an atomic sign's `phonetic_version` is still empty, or a sign has no Unicode identity at all, check the sign's own name against `diri_lexical_list.csv`, then `ogsl_sign_readings.json` | 185 rows given a reading by name |
| **Stage 5** *(v13)* | Fill the remaining **gaps** in the readings of simple signs with `osl.asl` `@v` values; record every disagreement instead of overwriting | 490 rows get 1,379 values; 748 conflicts recorded |
| **Stage 6** | Find every sign name of the merged syllabary **Syllabary_CM.csv** with no counterpart in Stage 1's output, and append it | 2,401 additional rows |
| **Stage 7** *(v13)* | Link these syllabary-only names to OSL where the link is unambiguous | 106 rows linked, 6 ambiguous |

**Output: `sign_catalogue_v13.csv`**, **10,573** rows (8,172 from OSL + 2,401 from the syllabaries), plus `osl_reading_conflicts_v13.csv` (748 rows).
**Script:** `06_build_sign_catalogue_v13.py` (formerly `2_build_allograph_pipeline_v13.py`).

**What changed since version 11 (9,603 rows):**
| Version | Change | Effect |
|---|---|---|
| v12 | A `@sign` that has `@form` entries now gets a row of its own (its own code point and readings) **before** the rows of its forms. In v11 only the forms were written | 217 Unicode signs (KA, SUM, TE, GAN, GUL, IL₂, U …) had no "Single Sign Reading" row, so their readings (ka, du₁₁, inim, šum₂ …) could not be resolved by the parser |
| v13 | OSL `@v` values fill gaps in simple-sign readings (Stage 5) | e.g. ṣi, ṣa, ṭa₃ were missing |
| v13 | Syllabary-only names linked to OSL (Stage 7) | e.g. the syllabary name PA3 (= pa₃ of \|IGI.RU\|) no longer hides the compound reading from the parser |

## Step-by-Step Description
The table is constructed so that each line describes a single sign: a simple sign occupies one entire line; a compound sign is split into several consecutive lines, one line for each sign that makes it up.

All of these lines share the fields that describe the compound as a whole (its full name, its full glyph, its reading), and differ only in the fields that pertain specifically to the current component (its own Unicode code, its own glyph, its position within the sequence).
This means that the same table can be read at the level of both a single sign and the compound as a whole, without duplicating the structure.

### 1. Parsing Full Coverage At The Sign Level
- The parser walks every `@sign` block in `osl.asl`.
- The sign itself is written first, with its own code point and readings (fixed in v12).
- If the block contains one or more `@form` sub-blocks, each form is then processed as its own entity, with the parent `@sign` header kept as a fallback: if the form has no code of its own, it receives the parent's code, recorded as `structural_hint = inherited_from_parent`.
- If a sign has no `@form` sub-blocks at all ("headless", in the terminology of this project), the `@sign` header's own data becomes the sign's entire row in the dataset.

This gives complete coverage of `osl.asl`: 3,249 `@sign` blocks, of which 40 are `@fake` and excluded, so **3,209 signs** and **4,423 entities** (signs + forms).
- A systematic audit of every `@`-tag in the file found further markers that affect this parse:

| Marker | Meaning | In osl.asl |
|---|---|---|
| `@sign-` | Entry explicitly flagged spurious / deprecated / "do not use" by the editors of `osl.asl` | 60 |
| `@form-` | Same convention, at the form level | 31 |
| `@fake 1` | The entry is physically present in the list for technical reasons, but its status as a real, independent cuneiform sign is not recognised | 40 |

**Note:**
**Headless** means the sign has no attested alternate catalogue name (terminology of this project).

### 2. Subdividing Signs Into Three Types (`sign_type`)
All signs are divided into three type groups (this `sign_type` describes the Unicode status and is a different notion from `sign_type` = LOGO / SYLL in grapheme.csv):

| Value | Condition | Rows |
|---|---|---|
| `Type_1` | Entity has its own Unicode code (`@list U+...`) | 1,351 |
| `Type_2` | Entity has a `@useq` (sequence of several Unicode characters for displaying or encoding a specific cuneiform sign: ligature, compound sign, or complex glyph), or a `×` / `&` name whose components each have their own code. The whole sign has no code of its own | 6,185 |
| `Type_3` | Neither own code nor a resolvable decomposition (e.g. \|GA₂×(A.EN)\|) | 3,037 |

**Type_1** unites signs that have received their own, indivisible status in the Unicode standard. From a historical writing perspective, these are signs that the modern coding system recognises as basic units of the cuneiform repertoire, that is, graphemes that cannot (or should not) be decomposed into simpler components for digital representation. A sign receives an atomic code when it is perceived as an independent written unit, regardless of whether it is a simple form (like A) or a historically complex sign.

**Type_2** describes signs that lack their own atomic identity, but are represented as a combination of already encoded signs. This reflects mechanisms of cuneiform development: the ability of scribes to create new graphemes by combining (juxtaposition with ×), ligature (&), or sequential writing (.) of existing signs. These signs are "read" through their components, not as an independent unit. Type_2 captures the compositional nature of writing.

**Type_3** is a residual category for signs that fall into neither group. It encompasses diverse phenomena, all united by the absence of a formal digital status:
- graphic variants of existing signs (positional modifications of the same basic sign, like A@g, A@t);
- signs known exclusively from historical paper catalogues (Deimel, Messerschmidt, and other pre-modern systems) for which digital encoding has not yet been done (like LAK240, BAU067);
- signs whose composite nature is evident from their name, but whose decomposition is not documented in the source;
- all signs that come only from the historical syllabaries (Stage 6).

Synthetic placeholder entities marked `@fake 1` in `osl.asl` are not real signs at all: they are excluded from the dataset entirely, not merely classified as Type_3 (see Step 1 above).

This classification is purely structural (it does not interpret meaning).

### 3. Categorizing Signs Into Single And Compound (`sign_structure`)

`sign_type` alone is not sufficient to describe a sign's actual composition, because:
1. Most Type_3 signs are not compounds at all: they are glyph-variant markers (`A@g`, `A@t`) or names known only from historical paper catalogues (`LAK240`, `BAU067`), with no compositional structure whatsoever.
2. Some compound signs carry **both** their own Unicode code **and** a documented `@useq`: they became common enough to receive a dedicated atomic code, while their compositional origin remains separately recorded (`|DUB.TI|`).

**Resolution 1: `sign_structure` column**

| Value | Condition | Rows |
|---|---|---|
| `atomic` | Own code, no `@useq` (or a code inherited from the parent sign) | 1,546 |
| `atomic_with_decompositions` | Own code **and** documented `@useq` | 4 |
| `compound` | No own code, but a component decomposition exists (explicit `@useq`, or algorithmically resolved from `×` / `&`) | 6,185 |
| `not_identified` | No own code, no resolvable decomposition | 2,838 |

**Resolution 2: `structural_hint` column**

| Value | Meaning | Rows |
|---|---|---|
| *(empty)* | No special condition | 9,970 |
| `inherited_from_parent` | Row has no code of its own; `unicode_id` was inherited from the parent `@sign` (e.g. an archaic catalogue form such as `LAK797` inheriting the code of its modern equivalent `A`). Kept out of `not_identified` deliberately, since the row *does* carry a usable Unicode value | 199 |
| `compound_unresolved` | Name contains `×` or `&` (structurally a compound) but its decomposition could not be resolved automatically, because of nested parentheses (e.g. `\|GA₂×(A.EN)\|`) or because a named component was not found in the sign index. `sign_structure` is `not_identified`, but the hint preserves the suspicion for manual review | 107 |
| `phonetic_via_diri` | Reading found in `diri_lexical_list.csv` by sign name, after the Step 1 / Step 3 joins left `phonetic_version` empty (see Step 6) | 17 |
| `phonetic_via_ogsl` | Same, but the reading came from `ogsl_sign_readings.json`; checked only when Diri had no reading either | 168 |
| `unicode_via_osl_name` *(v13)* | Syllabary-only name that is an OSL sign name with its own code point: the code point is filled | 19 |
| `unicode_via_osl_value` *(v13)* | Syllabary-only name that is an OSL value of exactly one simple sign: that sign's code point is filled | 53 |
| `osl_value_of_compound` *(v13)* | Syllabary-only name that is an OSL value of exactly one compound (PA3 = pa₃ of \|IGI.RU\|): the row becomes a reference to that compound | 34 |
| `osl_value_ambiguous` *(v13)* | Syllabary-only name that is an OSL value of several signs: only marked, not linked | 6 |

**Note:**
**`@useq`** sequence of several Unicode characters (code points) for displaying or encoding a specific cuneiform sign (ligature, compound sign, or complex glyph).

### 4. Decomposing Compound Signs Into Components

For signs classified as `compound`, the component sequence is obtained in one of two ways:
1. Where `osl.asl` records an explicit `@useq`, the sequence is read directly (split by `.`).
2. Where no `@useq` is present but the sign's name contains `×` (juxtaposition) or `&` (ligature), the parser splits the name into pieces and looks up each piece as its own sign, for example splitting `AB×A` into `AB` and `A`.

To look up each piece, the parser checks only the list of `@sign` headers, never the `@form` names.

**Note:**
- **Nested parentheses.** A name like `|GA₂×(A.EN)|` has a compound inside another compound (the `(A.EN)` part is itself two signs, and it sits inside a larger ×-combination). The automatic splitting routine does not try to guess how to break this apart (a wrong guess here would be worse than leaving it unresolved). These are flagged as `compound_unresolved` instead.
- **`@compoundonly` shapes.** Sometimes one piece of a compound's name does not exist as its own sign in `osl.asl`: there is no `@sign` entry for it anywhere. Instead, `osl.asl` mentions that shape in a separate `@compoundonly` declaration (142 in our version). This shape has been seen, but only as part of some other compound; it has never been treated as a sign on its own.

Every compound entity is then exploded into one row per component, and four columns together reveal its full composition:
●	**`component_position`** numeric position of the component in the compound sign (left to right).
●	**`compound_form`** the name of the compound as a whole, identical across all of its component rows.
●	**`compound_grapheme`** the full glyph sequence of the compound (not the single-component glyph).
●	**`compound_unicode`** the semicolon-separated list of all component codes, in sequence order.

Each row's own `unicode_id` and `sign_grapheme` (columns 1 and 2) describe that one component specifically, while `compound_form` / `compound_grapheme` / `compound_unicode` describe the compound as a whole, so a single compound sign is fully readable both at the component level and as an aggregate from the same set of rows.

### 5. Assigning `osl_form_id`

Each sign's distinct documented `@form`s (catalogue variant or glyph version) are numbered `{PREFIX}_v1`, `_v2`, … in the order they are **documented in `osl.asl`**. All component rows belonging to one compound form share the same id, since they represent one attestation, not separate variants.

**Note:** a `@form` is a *catalogue* variant recorded by the editors of OSL. It is not yet evidence of an allograph in a text: ATF does not record which form the scribe wrote (Stage 3 of the thesis).

### 6. Assigning Phonetic Version, Transliteration, And Syllabary Sign

●	**`unicodeTrLit`** the transliteration derived from the sign's Unicode character name.
●	**`syllabary_sign`** the scientific sign name as used in academic citation.
●	**`phonetic_version`** the full pipe-separated list of attested phonetic readings.
●	Every row is classified into exactly one of six **`typePhonetic_Version`** values:

| `typePhonetic_Version` | Condition | Rows |
|---|---|---|
| `Single Sign Reading` | atomic sign, joined by its own `unicode_id` against the Step 1 catalogue | 3,917 |
| `Attested Compound Reading` | compound, whole-word reading found via Step 3's table | 4,238 |
| `No Attested Compound Reading` | compound, no reading found anywhere | 1,745 |
| `Compound Nested in Longer Form` | compound documented only inside a longer attested form | 202 |
| `No Sign Identity` | no Unicode code, no decomposition | 437 |
| `Syllabary Name Of OSL Compound` *(v13)* | syllabary-only name that is the OSL value of exactly one compound (Stage 7) | 34 |

For compound rows, every component row of the same compound carries the **same** `phonetic_version`: the compound's own whole-word reading, following the same convention as `compound_form` / `compound_grapheme` / `compound_unicode`.
The compound's reading describes the word as a whole, not any single component. Where no compound-level reading is attested, the field is left empty.
`Compound Nested in Longer Form` rows are, by design, always empty in `phonetic_version`: that status specifically means no reading of the short form's own exists (explained in `nested_in_forms` in `compound_form_reading_table_v13.csv`).

For atomic rows, an empty `phonetic_version` happens for one of two reasons: either the Unicode code that `osl.asl` claims for the sign is not one of the 1,234 officially ratified codes, or the code is legitimate but no reading for it was recorded in the Step 1 catalogue (7_unicodePhoneticVersion_full.csv).

The Step 1 catalogue is searched by `unicode_id` only. It can only help a row that already has a working Unicode code listed there. For the remaining rows, a second search is made by the sign's own **name** instead of its code: `diri_lexical_list.csv` and `ogsl_sign_readings.json` are both organised by sign name, so they can still return a reading where the Unicode-based search could not. Diri is always checked first, OGSL only as a fallback, the same priority order as for compound readings in Step 3. This is applied in two places:

●	**`Single Sign Reading` rows with an empty `phonetic_version`:** 66 rows closed (4 via Diri, 62 via OGSL; `structural_hint` set to `phonetic_via_diri` or `phonetic_via_ogsl`).
●	**`No Sign Identity` rows** (no Unicode code at all, 437): **119 given a real, attested reading** (13 via Diri, 106 via OGSL), direct evidence that "not encoded in Unicode" and "not linguistically attested" are two different facts about a sign.

**Gap filling from OSL @v (v13).** After these joins, a `@v` value of a sign (or form) in `osl.asl` is added to its simple-sign row **only if no simple-sign row of the catalogue has this reading yet**. Existing readings are never moved to another sign. 490 rows received 1,379 values in total; they are listed in the new column `osl_v_added`, so every added value stays traceable.
When OSL gives a reading to a different sign than the catalogue (e.g. mur₂: MURUB₄ in OSL, NISAG in the catalogue), nothing is changed: the case is written to **`osl_reading_conflicts_v13.csv`** (748 rows: `reading`, `osl_sign`, `catalogue_sign`). Following the rule of the project, disagreements between sign lists are recorded, not hidden.

After all stages, 215 `Single Sign Reading` rows still have no reading, and 9 of the 1,234 Unicode signs have no `Single Sign Reading` row at all: U+12003, U+1207F, U+12153, U+121B1, U+121F9, U+12358, U+122AA and U+12376 (both only under a deprecated `@sign-` entry in OSL), U+1243A (absent from OSL).

### 7. Extending The Dataset With Signs Outside osl.asl

Every one of the 4,196 distinct sign names in the merged syllabary (**Syllabary_CM.csv**) is checked against every sign already classified in Stage 1 (normalised: pipes stripped, Unicode subscript digits folded to ASCII). Names with no counterpart are appended: **2,401 rows** (Uruk2 2,109, Syllabary_CM 247, Additional Sources 45).
The overwhelming majority come from the archaic proto-cuneiform Uruk period (3400–3000 BCE).

**Classification of the additional syllabary signs**, due to the lack of an information source:
- `sign_type = "Type_3"`, `sign_structure = "not_identified"`, identical to any other sign without a Unicode identity;
- `sign_source`: `"Uruk2"` / `"Syllabary_CM"` / `"Additional Sources"`;
- every field that cannot apply to them (`unicode_id`, `sign_grapheme`, `compound_form`, `compound_grapheme`, `compound_unicode`, `unicodeTrLit`, `signList_analogue`) is left empty;
- `typePhonetic_Version`: they do carry a real, attested reading; that is the entire reason they are included.

**Linking to OSL (v13).** A syllabary-only name gets an OSL identity only when the link is unambiguous:
| Case | Rows | Result |
|---|---|---|
| the name is an OSL sign name with its own code point | 19 | `unicode_id` filled (`unicode_via_osl_name`) |
| the name is an OSL value of exactly one simple sign | 53 | that sign's `unicode_id` filled (`unicode_via_osl_value`) |
| the name is an OSL value of exactly one compound | 34 | row becomes a reference to that compound (`Syllabary Name Of OSL Compound`, `compound_form` filled) |
| the name is an OSL value of several signs | 6 | only marked (`osl_value_ambiguous`) |
| no OSL match | 2,289 | unchanged |

### 8. Role Of The Other Historical Catalogues (`signList_analogue`)

Beyond Unicode, `osl.asl` cross-references each sign against up to fifteen other historical sign-list systems (`LAK`, `MZL`, `RSP`, `ABZL`, `ELLES`, `KWU`, `BAU`, `ASY`, `GCSL`, `PTACE`, `HZL`, `SYA`, `ZATU`, `REC`, and others). These are not Unicode codes, they are references to paper catalogues compiled at different points in history, each associated with a particular period and scholarly tradition (`LAK` for the Uruk archaic corpus, `ABZL` for Old Babylonian school texts, `MZL` for Standard Babylonian). `signList_analogue` collects every such reference attached to a sign, annotated with its approximate period and region, into one semicolon-separated field. Its role in this dataset is traceability: it lets a sign found in this table be cross-checked against the specific secondary-literature catalogue a philologist would recognise, and it gives an approximate chronological / regional anchor for a sign even before any corpus text has been joined.

### 9. `@compoundonly` Investigated, No Fix Required

`osl.asl` separately declares sign names via a standalone `@compoundonly` directive (142 declarations), outside any `@sign` block, acknowledging that a given shape exists only as part of another, already-documented compound. None have their own `@sign` entry at all. See Step 4 above for its one confirmed, narrow effect on `compound_unresolved` decomposition.

**Note:**
**"headless"** all of the sign's information sits in the `@sign` header, with nothing catalogued as an alternate name.
**"X"** as a component value is a placeholder for an undeciphered sign. 181 rows contain X in `unicode_id` or `compound_unicode`; these rows should be excluded from any Unicode-keyed join.
**"[unverified]"** suffix on a `unicode_id` (101 rows) marks a code that `osl.asl` records but that is not present in the canonical 1_unicodeSigns.csv reference. Inspection of the `@uage` field for these entries shows they are not unsourced errors: they carry values such as ACN or a Unicode Technical Committee document number (e.g. L2/24-270), indicating the code has been formally proposed to the Unicode Consortium but not yet ratified in a published version.
**"not_identified"** (in `sign_structure`) rows have no usable `unicode_id`; some of them are structurally suspected compounds that could not be decomposed automatically (`structural_hint = compound_unresolved`).
