##  1. How Are The Unicode ID And The Phonetic Versions Assigned?

This step establishes a catalogue that assigns to every cuneiform sign in Unicode its unique identifier and its full range of phonetic transliteration values.

The goal is to create a single reference table as the lookup layer for all subsequent corpus parsing. When an ATF text contains a token such as 'sila₃' or lamma(GURUŠ), the pipeline must be able to answer two questions:
- Which Unicode sign does this token refer to?
- What is the full set of phonetic values this sign can carry?

**The first stage of the pipeline is to assign: Unicode ID + Phonetic Version table.**

*Figures: pipeline run of 22 November 2026.*

Our version has 3,309 @sign blocks; 1,215 of them carry a Unicode ID.|

## Pipeline Overview

The pipeline processes the Unicode sign list in two passes:
1. The first pass matches signs to the professor's syllabary. **OSL decides which sign a code point is**; the syllabary gives the readings when it names the same sign.
2. The second pass describes the remaining signs from the ORACC Sign List.

---
Both outputs are merged into a unified table of **1,234** entries.

|Stage|	Input|	Output|
|---|---|---|
**Stage A**|1_unicodeSigns.csv + syllabary_CM.txt, additional_signs.txt, syllabary_uruk2.txt + osl.asl|3_matched_signs_full.csv (779) + 4_unmatched_for_review.csv (455) + step1_syllabary_osl_disagreements.csv (18)|
**Stage B**|4_unmatched_for_review.csv (455) + osl.asl|5_restUnicodeSigns.csv (455): 436 with a sign name (256 of them also with readings) + 19 without a sign name*|
**Stage C**|3_matched_signs_full.csv (779) + 5_restUnicodeSigns.csv (455)|7_unicodePhoneticVersion_full.csv: 1,234 signs|

*Of the 19 signs without a sign name, 16 appear in osl.asl only as @form (a form of another sign), 2 only under a deprecated @sign- entry, and 1 (U+1243A) is absent from osl.asl.

## Step-by-Step Description
### 1. Build the Syllabary (Syllabary_CM.csv)
Three source files were merged into a single, unified syllabary:     
●	**syllabary_CM.txt** the main phonetic mapping compiled by Professor Massimo Maiocchi: 19,274 entries.    
●	**syllabary_uruk2.txt** archaic Uruk-period sign names: 2,212 entries.    
●	**additional_signs.txt** supplementary entries for rare or compound forms: 65 entries.    
Each line in the merged file follows the format: phonetic_reading to SIGN_NAME, with the column source (CM / URUK2 / ADDITIONAL). Two of the input files start with a byte-order mark, which is removed when the files are read. Of the 21,551 raw entries, 91 duplicates were removed (90 from URUK2, 1 from ADDITIONAL), which gives **21,460** entries.

**Output: Syllabary_CM.csv** (21,460 rows: CM 19,274, URUK2 2,122, ADDITIONAL 64).

**Script:** 01_build_syllabary_CM.py.

### 2. Download and Prepare the Unicode Sign List
The complete list of cuneiform Unicode code points was obtained from the Unicode Consortium's three cuneiform blocks (U+12000–U+12543).    
**Links**: https://www.unicode.org/charts/PDF/U12000.pdf, https://www.unicode.org/charts/PDF/U12400.pdf, https://www.unicode.org/charts/PDF/U12480.pdf     
**Resulting** in **1,234** signs.

**Each record contains:**    
●	**unicode_id** the code point (e.g. U+12000).     
●	**sign_grapheme** the rendered cuneiform character (e.g. 𒀀).     
●	**transliteration** the Unicode character name converted to transliteration form (e.g. "a", "a × bad").     
  
**Output: 1_unicodeSigns.csv**      
This file becomes the left-hand side of all subsequent joins and defines the target set: every sign in the final catalogue must have a Unicode ID. It is also the list of **ratified** code points: a code point outside it (only proposed to Unicode) is marked `[unverified]` in the later steps and is not used to build compound signs.

### 3. First Join: Unicode List × Syllabary (Stage A)
The Unicode sign list is joined against the three syllabary files (the same sources as Syllabary_CM.csv, read in the order CM, ADDITIONAL, URUK2).

**Normalisation.** Unicode names and syllabary entries are written in different conventions (Unicode: "ash₂", "a × gan₂ tenu"; syllabary: "AŠ2", "A×GAN2@t"). Both sides are brought to one normalised form before matching:   
●	subscripts become digits, × becomes X;    
●	the Unicode modifier words become ATF modifiers: GUNU → @G, TENU → @T;     
●	the English spelling SH becomes Š (ASH → AŠ, GISH → GIŠ, SHESH → ŠEŠ);     
●	THREE becomes X3; the dots of DAG.KISIM5 and NUNUZ. are restored;     
●	the descriptive words of the Unicode names are translated into the notation of the syllabary: **opposing** (the sign repeated twice, one against the other) becomes `X@Y` (EN@EN, LUGAL@LUGAL, LU2@LU2), **squared** (the sign repeated four times) becomes `X×4` (EN×4, IM×4, TAB×4, ZA×4×KUR); spaces are removed.     

**Candidate.** A Unicode sign is matched first by the normalised **sign name** of the syllabary, then by a normalised **reading**. If several candidates fit, the first one found is taken.

**OSL decides which sign it is.** A match through a reading can lead to a **different** sign: the syllabary gives the reading *duh* also to GABA, so the character U+12083 ("duh") would be taken for GABA and receive its readings. OSL, however, records the code point of every sign directly (`@list U+12083` → DUH). The candidate is therefore checked against OSL:
1. The sign is the one that OSL gives to the code point.
2. If the syllabary candidate names the same sign (in any notation: GA2×A+HA = |GA₂×(A.HA)|, EN×4 = |4×EN|), the syllabary readings are used (**776 signs**);
3. if the syllabary names another sign, the syllabary sign with the OSL name is used, when it exists (**3 signs**: ARKAB₂, NU₁₁@t, |SAL.TUG₂|; a variant form such as KALAM~a never replaces a sign);
4. otherwise the sign is not matched here and is described from OSL in Stage B (**15 signs**);
5. signs without an own OSL code point keep the syllabary match.

All 18 disagreements between the syllabary and OSL are listed in `step1_syllabary_osl_disagreements.csv` (sign, Unicode name, syllabary sign, OSL sign, decision) for review against MZL (file **P11** of the manual check). Examples of the effect in the corpus: *kalam* → KALAM (1,097 tokens), *gaba / gab* → GABA (893), *na₄ / ia₄* → |NI.UD| (490).

The join produces three outputs:       
●	**3_matched_signs_full.csv (779 signs)** signs found in both the Unicode list and the syllabary. Each matched sign receives its syllabarySign (scientific name) and PhoneticsVersion (all readings of that sign in the syllabary, separated by " | ").      
●	**4_unmatched_for_review.csv (455 signs)** signs present in the Unicode list but not matched to the syllabary, including the 15 signs that the syllabary names differently from OSL. These are mainly signs with a purely descriptive Unicode name: stacked signs (AN / AN), crossing signs (BU crossing BU), the modifiers ZIDA and KABA, and rare compounds. The column translit_normalized shows the form that was searched for.      
●	**step1_syllabary_osl_disagreements.csv (18 signs)** for review.

|Output file|Count|Status after Stage A|
|---|---|---|
|3_matched_signs_full.csv|779|Complete: unicode_id + phonetic values assigned|
|4_unmatched_for_review.csv|455|Partial: unicode_id only, no phonetic values yet|
|Total|1,234|Covers the full Unicode cuneiform blocks|

**Script:** 02_join_unicode_syllabary_CM.py

### 4. Second Join: Unmatched Signs × OSL (Stage B)
The 455 unmatched signs are processed against the ORACC Sign List (osl.asl). The OSL file is structured into @sign blocks, each identified by a @list U+ tag that links the sign to its Unicode code point.

For each unmatched sign, the parser:    
●	searches the OSL for a @sign block whose @list U+ matches the sign's unicode_id;    
●	takes the scientific sign name from the @sign line for the column syllabarySign;    
●	collects all @v (phonetic value) entries of that block for the column PhoneticsVersion (separated by " | ").     

**Output: 5_restUnicodeSigns.csv**.
|Sign|Count|Description|
|---|---|---|
|Found in OSL, with sign name and readings|256|-|
|Found in OSL, sign name only|180|The @sign block has no @v values: 151 Early Dynastic signs, 21 signs of the main Cuneiform block, 8 numerals or punctuation signs.|
|Not found as a main @sign in OSL|19|16 appear only as @form (a graphic form inside another @sign block; the reading is inherited from the parent sign); 2 appear only under a deprecated @sign- entry (U+122AA \|SAL.LAGAB×AŠ₂\|, U+12376 \|DUB×ŠE\|); 1 is absent from osl.asl (U+1243A).|
|Total|455|Phonetic fields left empty where unavailable|

**Script:** 03_build_rest_unicode_signs.py.

### 5. Merge: Final Catalogue (Stage C)
The two output files of Stages A and B are joined into a single unified catalogue, in the order of 1_unicodeSigns.csv:
|Source file|	Records|	Notes|
|---|---|---|
|3_matched_signs_full.csv|779|Full phonetic coverage from the syllabary|
|5_restUnicodeSigns.csv|455|Sign names from OSL (436), readings from OSL @v (256)|
|Total|1,234|Covers the complete Unicode cuneiform blocks|

**Output: 7_unicodePhoneticVersion_full.csv**

**Script:** 04_join_matched_rest_signs.py 

## Output Description
Output: 7_unicodePhoneticVersion_full.csv
Total signs in the Unicode cuneiform blocks: **1,234**.
|Coverage|Signs|
|---|---|
|with a scientific sign name|1,215|
|with at least one reading|1,035 (779 from the syllabary + 256 from OSL)|
|without a sign name|19 (see Stage B)|

The PhoneticsVersion column deliberately records all attested readings for each sign, not only the most common one.

All records share the same schema:
- **unicode_id** - Code point in U+XXXXX format. Primary key. Unique per sign. Source: Unicode Consortium
- **sign_grapheme** - Rendered cuneiform character. One character for simple signs, and a sequence for compound signs that lack a unified code point. Source: Unicode Consortium
- **unicodeTrLit** - Human-readable transliteration of the Unicode character name. Describes the graphic composition of the sign (e.g. "a × bad" for A×BAD). Source: Unicode Consortium
- **syllabarySign** - Scientific sign name as used in Assyriology (e.g. A, SILA₃, |AN.KI|). Standard identifier used in sign lists and cited in publications. Source: Syllabary_CM / OSL
- **PhoneticsVersion** - All attested phonetic readings of the sign, separated by " | ". Encodes the full polyphony of each grapheme. Central input for phonetic analysis. Source: Syllabary_CM / OSL

**Next step:** the gaps left here (signs without readings) are filled in the full sign catalogue (Steps 3–4): readings from OSL @v are added only where the catalogue has none, and every disagreement between OSL and the catalogue is recorded in a separate file instead of being overwritten (file **P10** of the manual check).
